## Persistence, autosave, and bid versions

Primary project files are stored as `data/projects/<stable-project-id>.json`. Backups are stored under `data/backups/<stable-project-id>/`. Configuration versions and exports have separate directories. Existing primary files are copied to the project backup directory before replacement. A new file is written to a temporary sibling, flushed and `fsync`ed, then atomically installed with `os.replace`. Backup retention defaults to 20. Expected file revisions detect concurrent-tab conflicts. Malformed primary JSON can be opened from the newest valid backup and restored through an audited recovery operation.

The user originally requested automatic saves every 10 seconds when a data change occurred. The current implementation instead records committed form changes after a 250 millisecond browser-event debounce and initiates an immediate save; the schema currently records `autosave_seconds: 0` and `autosave_debounce_ms: 250`. Rapid changes can share one atomic write, overlapping saves are prevented, and the UI shows Saving, Saved, Unsaved changes, Save failed, or Save conflict. This difference must be discussed explicitly. Determine whether the desired behavior is a true ten-second dirty flush, a ten-second maximum save latency with debounce, the current near-immediate persistence, or a hybrid. Consider disk-write frequency, user expectations, multi-tab conflicts, bid-version noise, perceived responsiveness, and recoverability.

The application maintains two independent version concepts. The JSON `revision` is a concurrency/persistence counter. The visible bid version is `Bmajor.minor.patch`. Each committed datapoint modification or recorded action increments patch. Submission increments minor and resets patch. Notice-to-proceed activation increments major and resets minor and patch. Multiple fields within one autosave write still produce multiple datapoint audit events and patch increments. Discuss whether this version model is understandable to estimators, whether every keystroke-level committed value deserves a public patch increment, and whether working edits, formal bid revisions, and audit-event counts should remain separate concepts.

Identify endpoints where dictionaries and loosely structured payloads should become typed request/response models. JSON-per-project storage is appropriate for local operation and owner inspection, but discuss its practical limits. ## Improvement areas to explore

Begin with the estimator's lived workflow. Ask what information arrives first, what is copied repeatedly, which inputs take the most time, where current workbook mistakes occur, what reviewers actually inspect, what must be visible at a glance, and what information Project Management wishes estimating had preserved. Look for ways to reduce duplicate entry, make missing scope visible, compare vendor quotes, preserve assumptions, and trace final price without overwhelming the user.

Evaluate information architecture. The current navigation mirrors workbook domains, which aids migration, but a web application may benefit from task-oriented stages, cross-stage readiness indicators, a review dashboard, global validation summary, calculation drill-down, and role-specific views. Recommend changes only when they preserve the ability to locate familiar workbook functions and understand where numbers go later.

Evaluate calculation transparency. A reviewer should be able to start at bid value and trace through selling lines, markup, tax, contingency, bond, quotes, frame/material takeoff, labor, equipment, rates, alternates, and configuration. Discuss whether the current lineage presentation is sufficient, which explanations should be inline, which belong in drill-down panels, and how to compare revisions.

Evaluate lifecycle controls. Clarify the distinction among working save, checkpoint, internal review, submitted bid revision, resubmission, award pending, notice-to-proceed activation, Project Manager re-estimate, approved change order, SOV revision, and closeout. Identify where the UI should block actions, request evidence, require a reason, or create an immutable snapshot.

Evaluate review and collaboration. The local app currently models roles but not actual people, assignments, comments, notifications, or signatures. Discuss the minimum useful review record for a local application and what should wait until identity and hosting are approved. Avoid designing an enterprise collaboration suite prematurely.

Evaluate reporting and outputs. Consider estimate summary, cost-code analysis, quote comparison, margin sensitivity, alternates, proposal, award variance, contract forecast, change-order log, SOV reconciliation, estimate-to-actual feedback, and portfolio reporting. Distinguish outputs needed for an individual bid from cross-project analytics that JSON-per-project storage may not yet support efficiently.

Evaluate accessibility and usability. Review keyboard navigation, focus handling, table editing, validation messages, mobile behavior, color-independent states, numeric formatting, dimension entry, long-form notes, destructive confirmations, unsaved-change behavior, and screen-reader semantics. The current responsive layout is visually designed, but passing unit contracts is not the same as a complete accessibility review.

Evaluate administration. Rates, cost codes, tax, wage records, schedule definitions, material factors, labor parameters, markup defaults, bond bands, PCO markups, permissions, and application settings need understandable versioning and activation. Discuss draft versus active configuration, change preview, dependency impact, approval, effective date, rollback, and testing before activation.

Continue maturing source control and release management from the local baseline: establish a branch strategy proportional to the project, a release/version convention, remote backup, dependency locking, automated checks, and deployment records before the first real project is entrusted to it.

## How to conduct the discussion

Start by summarizing your understanding of the current product in plain language and identify the five most consequential product risks or improvement opportunities. Then ask the owner a focused first batch of approximately five to ten questions. Group questions by decision area and explain why each answer changes the design. Do not dump a comprehensive questionnaire all at once.

For each recommendation, state the user problem, current evidence, proposed change, expected benefit, risks or tradeoffs, dependencies, and how success would be tested. Label it as immediate, near-term, later, or dependent on an unresolved owner rule. Separate low-risk improvements from changes that could alter commercial calculations, authority, or historical records.

Challenge inconsistencies constructively. In particular, discuss the ten-second autosave requirement versus current 250 millisecond immediate saving, user-facing bid patch increments versus keystroke-level audit detail, provisional approvals under unresolved policy, and the gap between local role selection and genuine authorization. Do not assume the existing implementation is correct merely because tests pass; tests can faithfully prove an unintended contract.

Do not modify files, create code, or provide a giant implementation plan in the first response. This handoff is for collaborative product discussion. Once the owner selects improvements, restate the accepted decisions, identify affected documentation and code, and propose a bounded implementation sequence with acceptance criteria.
